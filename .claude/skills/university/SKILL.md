# University — исследовательский конвейер знаний для проекта

Это адаптация шаблона `university-template` (изначально bash+TTY-скрипт) под работу
прямо внутри Claude-сессии — без терминала, без python-интервью с `input()`.
Полная методология обработки источников лежит в `references/METHODOLOGY.md` — читай
её перед первым запуском пайплайна и держи в контексте на всё время работы с
университетом.

## Когда что делать

1. Пользователь просит завести университет / впервые кидает ссылку в проект, где
   `university/` ещё нет → **Bootstrap** (ниже).
2. `university/` уже существует, пользователь кидает URL / "обработай X" →
   **Пайплайн обработки источника** (§4 в `references/METHODOLOGY.md`).
3. Пользователь спрашивает про состояние знаний по теме → прочитай
   `university/syntheses/<topic>.md`, при отсутствии — предложи собрать.
4. Пользователь спрашивает "что у нас со стратегией/кодом" → раздел §14
   методологии ("Мост к продукту").

## Bootstrap (первый запуск в проекте)

Если в корне текущего проекта нет папки `university/` — сначала предложи её
завести, объяснив в одном абзаце что это (база знаний с проверяемыми
утверждениями, привязанными к первоисточникам). Получив согласие, задай **прямо в
чате**, одним сообщением или по очереди (как удобнее пользователю), эти вопросы —
это замена интерактивного `interview.py`, TTY не нужен:

1. **Миссия проекта** — одно предложение. Пример: «обоснованно сконструировать
   стратегию безубыточной LP-торговли на Meteora DLMM».
2. **Seed docs** (опционально) — уже существующие в проекте документы, которые
   надо считать первичными внутренними источниками. Формат: `путь — описание`.
3. **In-scope темы** — что университет принимает к обработке.
4. **Out-of-scope темы** — что сразу отклоняется (защита от расплывания скоупа).
5. **Таксономия** — дерево тем листьями, формат `root/leaf — описание`.
6. **Пути к коду/докам** (опционально) — с чем сверять знания в §14 "Мост к
   продукту".

Не блокируйся, если пользователь не отвечает на опциональные пункты (2 и 6) —
оставь их пустыми, дозаполнить можно позже. После ответов покажи короткое
summary и спроси подтверждение, затем создай в корне проекта:

```
university/
├── METHODOLOGY.md   # references/METHODOLOGY.md, с {{PROJECT_MISSION}} и
│                     # {{PROJECT_NAME}} заменёнными на реальные значения
│                     # и разделами §1, §1.1, §2, §14 заполненными ответами
├── README.md         # короткое описание: миссия + как этим пользоваться
├── TAXONOMY.md        # дерево тем из ответа 5
├── INDEX.md            # пустая таблица (Sources/Notes/Claims/Syntheses/
│                       # Contradictions/Verdicts) — см. §13 методологии
├── sources/            # источники с conspect'ами (по одной подпапке на src-id)
├── notes/              # атомарные заметки n-<slug>.md
├── claims/             # проверяемые утверждения c-<NNNN>.md
├── syntheses/          # сводные документы syn-<topic>.md
├── contradictions/     # зафиксированные конфликты
├── verdicts/           # итоговые решения
├── experiments/        # свои бэктесты/симуляции, если есть
├── graph/edges.jsonl    # пустой файл — граф связей
└── queue/
    ├── inbox.md         # пустой
    ├── to-follow.md     # пустой
    └── escalation.md    # пустой
```

Шаблоны для `sources/<id>/meta.yaml`, `notes/n-*.md`, `claims/c-*.md`,
`syntheses/syn-*.md`, `contradictions/contr-*.md`, `verdicts/v-*.md`,
`sources/<id>/conspect.md` — в `assets/templates/`, копируй и заполняй их, не
изобретай формат заново.

После bootstrap — предложи закоммитить `university/` как часть проекта (или
сообщи, что сделаешь это в рамках текущего коммита, если пользователь уже просил
что-то закоммитить).

## Пайплайн обработки источника (когда `university/` уже есть)

Полный алгоритм — §4–§13 `references/METHODOLOGY.md` (fetch → relevance →
quality → conspect → atomize → claims → link extract → synthesis → graph →
index). Коротко:

- Читай `university/METHODOLOGY.md` конкретного проекта, а не общий референс —
  в нём уже подставлены реальные scope/taxonomy этого проекта.
- Не создавай дубликаты: перед обработкой URL проверь `canonical_url` во всех
  существующих `sources/*/meta.yaml`.
- Один источник — один вызов пайплайна до конца (conspect + notes + claims +
  index), не растягивай на пол-шага.
- Если что-то неочевидно (relevance, качество, конфликт) — не додумывай, кидай
  в `queue/escalation.md` и спрашивай пользователя (см. §16 методологии).

## Границы

- Никаких автоправок в коде проекта на основе знаний из университета — только
  после явного запроса пользователя (§14, §15 методологии).
- Одна идея — один атомарный note. Если видишь, что note расползается на две
  мысли — дели.
- Не резюмируй пустое содержание источника ("water-content") — в `_rejected/` с
  причиной.

## Синхронизация между устройствами

Если `university/` живёт в git-репозитории, к которому обращаются несколько
независимых сессий (компьютер, планшет, телефон), — не полагайся на то, что все
они автоматически видят изменения друг друга:

- **В начале работы с университетом** (перед bootstrap или перед пайплайном) —
  сделай `git pull`, чтобы увидеть, что добавилось с других устройств с
  последнего раза.
- **После любого добавления/изменения файлов университета** — `git add` +
  `git commit` (понятное сообщение) + `git push`, чтобы это увидели остальные
  сессии.
- Конфликт при `git pull` — не разрешай "на глаз". Файлы вида `notes/*.md`,
  `claims/*.md` обычно не конфликтуют (уникальные ID в имени файла), а вот
  `INDEX.md` и `graph/edges.jsonl` могут — покажи пользователю оба варианта и
  спроси, как объединять.

Это правило действует независимо от того, откуда идёт сессия — не только на
"компьютерных" сессиях: если сомневаешься, свежие ли у тебя данные, лучше
лишний раз сделать `git pull`, чем работать по устаревшей копии.

## Границы применимости этого скилла

Университет — по дизайну **per-project**: у каждого проекта свои миссия, scope
и taxonomy, поэтому bootstrap проходит заново в каждом новом проекте, где скилл
вызывается впервые. Сам скилл (эти инструкции + шаблоны) переиспользуется
одинаково везде, где он подключён — только заполненный `university/` внутри
конкретного проекта у каждого проекта свой.
